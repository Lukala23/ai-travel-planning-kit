# AI 旅行规划工具包：可复制提示词

[English](prompts.en.md)

把方括号内容替换成自己的信息。无需一次使用所有提示词。

Codex 中可以保留 `$plan-reliable-trips`；TRAE、WorkBuddy、Claude Code、Cursor、Windsurf、GitHub Copilot、Gemini CLI 或普通文件上传模式，请按 [平台指南](../docs/agent-platforms.md) 换成对应调用方式，或直接写“使用 AI 旅行规划工具包”。

## 1. 从自然语言建立任务卡

```text
使用 $plan-reliable-trips。

我要去【目的地】，日期是【完整日期】，共【人数】人。
已确定：【航班 / 住宿 / 演出 / 其他不可改变项目】。
预算大致是【预算或成本敏感度】。
这次最重要的是【核心目标】。

先不要排路线。请把信息整理成单次任务卡，区分：
已知事实、硬约束、软偏好、未知、临时假设。
只追问会改变安全、可行性、住宿区域、交通骨架或总预算的问题。
```

## 2. 先研究目的地，不急着排日程

```text
请先研究【目的地】的候选全集并筛选。

同时搜索经典地点、高价值小众地点、季节限定、博物馆和需要预约的体验。
不要把平台排名、点赞或网红程度当作价值。
输出 A / B / C 候选，以及少量我可能疑惑为什么没安排的 D 级地点。
同时告诉我住宿区域、交通结构和哪些决定必须先确认。
```

## 3. 生成可执行路线草案

```text
根据已经确认的候选和住宿区域生成路线草案。

计入门到门移动、排队、正常用餐、休息、行李、预约缓冲和安全返回。
普通观光默认平衡模式，但请用每日起止时间、步行 / 站立量、
硬预约和优先删减点描述实际强度。
备选只针对真实风险，写明触发条件和会改动哪些后续节点。
```

## 4. 住宿专项研究

```text
请把住宿作为路线核心重新研究【目的地】。

先比较区域，再比较具体住宿。统一日期、人数、房型、床型、早餐、
取消、税费和币种，给全程真实总价。
同时评价每日景点交通、机场 / 车站衔接、周边闲逛、当地饮食、
夜间返回、噪声和住宿本身的体验价值。
不要按单一平台评分直接推荐。
```

## 5. 国外支付、网络与交通防骗

```text
这是一次前往【国家 / 城市】的国外旅行。

请核验：
1. 公共交通对我的手机、银行卡和国际钱包是否真正可用；
2. 现金需求、换汇 / ATM 费用和抵达后的第一段支付；
3. 漫游、旅行 eSIM、本地 SIM 的设备兼容与主备方案；
4. 机场到酒店、主要包车和特殊交通的正常价格、计价单位与正规渠道；
5. 总价书面确认的当地语言话术；
6. 常见加价、币种偷换、平台外交易或扣留行李风险及求助方式。
```

## 6. 博物馆与中文理解

```text
请研究【目的地】真正值得纳入的博物馆、展馆和小型专业馆。

不要只看名气或馆藏总量，要核验当前实际在展、核心展区开放、
不可替代性、与其他馆的重复度和真实参观时间。
我是中文母语使用者，请核验官方中文标识、语音、App、中文团和私人中文导游，
明确说明是否值得请导游、当前价格与包含项，并给可执行馆内动线。
```

## 7. 摄影与参考图

```text
请扫描整条路线的拍摄机会。

我主要使用手机，最多加便携稳定设备。重点是构图、站位、方向、
光线、人物关系和避开杂乱，不要默认专业相机。
对必拍点和文字难以解释构图的常规景点，提供来源清楚的实际参考图，
说明借鉴什么、普通游客能否复现，以及是否依赖无人机、长焦、重后期或特殊季节。
长时间等待、明显绕行或牺牲核心体验的拍摄，只作为强化方案。
```

## 8. 审核我下载的徒步轨迹

```text
请使用 $plan-reliable-trips 审核我提供的徒步路线文件 / 链接 / 截图。

检查来源、名称、版本、日期、方向、距离、爬升、起终点、轨迹断裂、
异常跳点、错误支线、关闭 / 私人 / 限制路段，以及山屋、水源、
检查站、危险段、退出和接驳。
结合许可、天气、季节、日照、能力、保险、救援和通信，
给出“可用 / 条件可用 / 不建议使用”及必须修正项。
明确说明审核局限，不把它写成安全认证。
```

## 9. 审阅和修改一个模块规则或偏好

```text
请只审阅【主题】相关规则，不要先修改。

先说明：
1. 当前规则会让模型实际怎么做；
2. 我的意见属于安全底线、本次硬约束、可覆盖默认、软偏好还是单次参数；
3. 有没有把随口倾向扩写成僵硬规则；
4. 应修改哪个文件，会影响哪些输出。

不要建立长期偏好索引。然后给简化后的规则文本，等我逐条确认后再修改。
```

## 10. 生成正式资料包

```text
路线和关键选择已经确认。请生成正式旅行资料包：

- 00_开始这里.md
- 01_离线手机版.html
- 02_完整旅行手册.md
- 02_完整旅行手册.pdf
- media/
- 需要纸质备份时生成 01_出行速查卡.pdf（离线手机版的打印对应物）
- 本次需要时生成 03_打印应急版.pdf

所有版本必须来自同一 Markdown 权威源，写明旅行日期、版本、
生成日期、最近核验日期和复查节点。
PDF 必须有文本层、目录书签、内部链接和图片说明，不得是扫描版。
离线手机版从模板生成单文件离线网页，生成后在真实手机浏览器验收。
```

## 11. T-7 天更新

```text
请按 T-7 天标准更新这份资料包。

重新核验局地天气、临时关闭、施工、展厅 / 步道状态、餐厅、
主要班次和重要预约。先列出变化和受影响的路线节点，
只修改真正受影响的部分，再同步重建 Markdown、离线手机版、PDF 和速查卡。
```

## 12. T-48 小时重点复核

```text
请按 T-48 小时标准做最后复核。

重点检查天气预警、航班 / 列车 / 轮渡、步道或道路状态、
重要预约、集合点、入口、支付和网络备份。
输出“无需改变 / 必须调整 / 仍需人工确认”，
并明确每个调整对后续交通、用餐、预约和返回的影响。
```

## 13. 旅行中把手册交给 AI

```text
我上传的是截至【核验日期】的旅行手册。

回答时请指出依据的章节。涉及今天的价格、开放、班次、天气、
签证、道路或步道状态时，请重新联网核验。
请区分：
1. 手册原有事实；
2. 当前联网更新；
3. 你基于两者做出的新规划判断。
```

## 14. 当天下雨，重排但不要推翻全程

```text
今天【日期】的天气发生变化。请只重排今天和真正受影响的后续节点。

保护不可退预约、重要交通和安全返回。
说明删除、移动和替换了什么；新的交通与用餐怎样衔接；
哪些摄影、户外或夜间项目改到更合适的日期。
不要无理由重新生成整趟旅行。
```

## 15. 先核对最低成行条件

```text
请使用 $plan-reliable-trips，先不要搜索完整景点清单。
对【目的地 / 日期 / 天数 / 人数 / 预算 / 实际出发地与返程终点】说明最低成行条件：
旅行证件对应的入境 / 许可要求、往返长途交通、主要刚性成本和我提出的执行前提。
逐项标记“已满足 / 待确认 / 不满足”，再输出“可行 / 条件可行 / 明显不匹配 / 尚无法判断”。
即使没有发现明显阻断，也要提醒仍需办理、满足或临行复核的条件；有明确阻断时给 2–3 个最小调整方向。
```

## 16. 非徒步高海拔、用药与就医准备

```text
请使用 $plan-reliable-trips 规划【高海拔城市 / 普通观光路线】，本次不徒步。
预计睡眠海拔为【数值】，我有【只写相关健康类别】并携带【药品通用名 / 设备】。
请加载健康医疗模块，区分入境强制要求与健康建议，核验药品跨境、适应日、食水 / 媒介、
适合的医疗点、付款与撤离流程。需要医生决定的内容标为“需专业评估”，不要诊断或给剂量。
```

## 17. 租车与必要保险提醒

```text
请使用 $plan-reliable-trips 比较【目的地 / 日期 / 路线】的租车方案。
核验租车合同、CDW / LDW、第三者责任、免赔额、燃油 / 充电、收费标签、冬季装备、
跨境、道路救援和罚单。整体旅行险我会自行处理；只提醒本次强制保险证明、特殊活动、
偏远撤离或计划依赖信用卡保障等容易漏掉的事项，不做产品排名或完整保单对比。
```

## 18. 从中国境内实际出发地搜索机票并判断何时购买

```text
请使用 $plan-reliable-trips 为【人数】搜索【完整日期 / 可浮动范围】从【中国境内实际出发地】前往【首个旅行节点】、
并从【最后旅行节点】返回【实际返回地】的机票。舱等【……】，行李【……】，中转 / 红眼 / 自行转机容忍【……】，
机票预算和退改侧重【……】。

先比较实际出发地直出、一次中转和受保护联程；只有完整成本和风险确实更优时，再比较先乘高铁或国内航班
到其他中国枢纽的方案。优先检查当次可访问的携程、去哪儿、飞猪等中国市场渠道，再用航司直接渠道
核验库存、承运、行李、票价产品、退改和联程责任。把前置交通、跨机场、住宿、行李重托和误机风险
都计入，不要只比较国际段票面价。

最多给综合推荐、最低完整成本和更舒适 / 低风险三类真实候选，并判断“建议现在购买 / 设置价格提醒观察 /
等待条件明确 / 尚无法判断”。如果观察，请给当前完整价格、目标价或买入条件、跟踪平台和最晚决策日期；
没有实际定时能力时明确这是手动跟踪协议，不要承诺后台监控。不要套用统一的提前 20 天或 100 天规则，
也不要把价格提醒当成库存保证。
```
