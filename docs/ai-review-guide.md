# 与 AI 一起审阅和修改旅行偏好

[English](ai-review-guide.en.md)

**AI 旅行规划工具包（AI Travel Planning Kit）**允许你逐个模块审阅规则和可覆盖偏好。最重要的不是堆更多要求，而是让人与 AI 的讨论可审阅、可修改、可回退，并避免把一次旅行的个人条件误写成全局行为。

## 1. 先判断一条意见应该放在哪里

同一句自然语言可能被 AI 误解成完全不同的规则。修改前先分类：

| 级别 | 含义 | 示例 | 是否可由单次任务覆盖 |
|---|---|---|---|
| 安全 / 法律底线 | 不满足就不执行 | 关闭步道不走、不建议向公职人员付款 | 否 |
| 本次硬约束 | 这趟旅行不能违反 | 必须无障碍、这次不能驾驶 | 否；下一趟重新提供 |
| 可覆盖默认 | 模块在没有其他说明时采用 | 普通观光默认平衡密度 | 可以 |
| 软偏好 | 只作为加分项 | 喜欢有趣、便携、有当地特点的小礼物 | 可以，不应阻塞方案 |
| 单次参数 | 只属于这一趟旅行 | 人数、预算、目的地、是否度假 | 下一次必须重新采集 |

最常见的错误是把一句“我可能更喜欢……”扩写成全局硬标准。AI 必须先问：这句话真的会否决其他选择吗？如果只是个人条件或单次倾向，应留在任务卡；只有明确要改变工具包行为时，才修改对应专项模块。

## 2. 一次只审一个主题

不要让 AI 一次重写所有文件。推荐流程：

1. 选择一个主题，例如住宿、支付、博物馆或徒步；
2. 让 AI 摘要现有规则，不先修改；
3. 指出不符合真实意图的地方；
4. 让 AI 提出 2–5 条简化后的规则；
5. 逐条确认；
6. AI 修改对应执行文件、审阅记录和必要的单次表字段；
7. 重新搜索旧表述，避免同一规则在其他文件中残留；
8. 执行技能结构校验；
9. 提交 Git 变更。

## 3. 推荐的审阅提示词

```text
请只审阅【主题名称】。

第一步不要修改文件，先告诉我：
1. 当前规则实际会让模型怎么做；
2. 哪些属于安全底线、长期硬约束、默认偏好、软偏好或单次参数；
3. 有没有把一句随口偏好扩写得过细、过硬；
4. 有没有因为规则太复杂而妨碍真实旅行决策。

然后用简洁、可执行的语言提出修改建议，等我逐条确认。
```

确认后：

```text
按刚刚确认的内容修改。

请同时更新：
1. 真正执行的规则文件；
2. 审阅记录；
3. 只有确实属于单次输入时才修改任务表。

修改后列出文件、核心变化、仍存在的不确定项，并检查旧表述是否残留。
```

## 4. 要求 AI 说明“影响范围”

每次修改都应回答：

- 哪个文件是权威来源；
- 哪些任务会加载这条规则；
- 它会改变候选筛选、路线、费用、风险还是交付格式；
- 是否会给用户增加新的必填项；
- 是否会与安全、法律或其他已确认规则冲突；
- 是否只是文案变化，还是决策行为变化。

如果 AI 不能解释影响范围，就不应立刻接受修改。

## 5. 不要轻易增加必填项

单次表的字段只有在答案会明显改变以下内容时才值得询问：

- 安全或合法性；
- 路线是否可行；
- 住宿区域或交通骨架；
- 总预算或不可逆预订；
- 同行者能否参与；
- 用户明确要求的核心体验。

其他信息可以：

- 从自然语言提取；
- 作为未知保留；
- 使用明确的临时假设；
- 在真正相关的模块出现时再问。

## 6. 保持规则的适当自由度

好的旅行约束通常是判断标准，不是固定答案。

较好的写法：

> 默认减少没有体验收益的换住宿；景观酒店、山屋、历史建筑或其他体验型住宿的独特价值足够时，可以主动换住，并说明搬迁成本和天气失败风险。

较差的写法：

> 一趟旅行最多换一次酒店。

较好的写法：

> 偏手工、少见、不易复制是纪念品的加分项，不是门槛。

较差的写法：

> 只允许购买完全手工、没有机器参与的纪念品。

## 7. 事实规则与偏好规则分开

以下内容不是偏好，不能由“我这次想这样”覆盖：

- 签证、许可、法律和正式收费；
- 当前开放、关闭和运营状态；
- 天气预警、道路和步道危险；
- 支付系统真正支持的卡、钱包和设备；
- 保险承保范围和救援条件；
- 用户没有提供但模型也无法查证的事实。

偏好只决定在多个合法、可行方案之间怎样取舍。

## 9. 修改后的验收清单

- [ ] 规则分类正确，个人条件和单次信息留在任务卡；
- [ ] 没有把软偏好变成否决条件；
- [ ] 没有增加无必要的每次必填项；
- [ ] 使用者能看懂标题和状态词；
- [ ] 同一事实没有在多个文件出现互相矛盾的版本；
- [ ] 通用专项规则只有一个权威文件，没有另建长期偏好索引或重复其正文；
- [ ] 条件加载矩阵能让模型找到新规则；
- [ ] 安全与法律优先级没有降低；
- [ ] 动态事实仍要求当次核验；
- [ ] 审阅记录与执行规则同步；
- [ ] 技能验证通过。

## 10. 常见反模式

### 把用户原话当成精确规范

用户说“我喜欢本地一点的东西”，不等于需要建立材质、生产设备和供应链审查制度。

### 固定旅行规划顺序

目的地探索、住宿、路线、徒步和更新可以并列组合。不是每次都要走“景点 → 酒店 → 交通 → 吃饭”的固定瀑布流程。

### 用更多字段代替更好的判断

表格越长不代表信息越充分。用户无法准确回答的“松弛 / 平衡 / 紧凑”不应成为强制选项，应改用每天起止时间、步行量、硬预约和删减点描述。

### 用流畅文案掩盖未知

无法核验时写“尚不确定”或“出发前复查”，不要补一个看起来合理的价格、入口或班次。

### 让每个模块都出现在最终攻略

模块化约束的目标是按需加载。没有徒步就不输出徒步章，没有值得专程拍的点就不制造摄影任务。

## 11. 使用 Git 保存可回退的讨论结果

推荐每个主题形成一个独立提交，例如：

```text
clarify accommodation trade-offs
add taxi fare and scam checks
simplify souvenir preferences
define track review workflow
```

提交前阅读 diff，确认没有把本地路径、订单、联系方式、证件或其他私人信息带入公开仓库。重大规则变化应在 Pull Request 中说明：

- 修改了什么；
- 为什么修改；
- 对使用者和输出有什么影响；
- 怎样验证；
- 有哪些仍未解决的边界。
